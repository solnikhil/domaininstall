# domaininstall feature research — multi-agent evaluation

Generated by workflow `feature-research`.

## Method

- Research agents: 15 (market, prior art, security trends)
- Score agents: 40 (one per feature candidate)
- Skeptic agents: 40 (adversarial kill-criteria)
- Measure agents: 40 (north-star + experiment design)
- Synthesize agents: 2 (primary + conservative)
- **Total logical agents: 137**

## Product constraints (fixed)

- Zero external publisher adoption; Milestone 4 not started
- Non-goals: malware scanner, attestation system, registry, replace provenance
- Bets: setup → resolve/API → CI policy → spec → other ecosystems

## Research highlights

### DNS TXT registrar onboarding friction

- Disconfirming (partial): TXT publish is already a mainstream publisher skill path—Google Workspace/Search Console, SPF/DKIM/DMARC, SSL domain checks all train the same Add TXT → wait → recheck loop—so domaininstall is not inventing a foreign mechanism, only a permanent (non-removable) mapping instead of a one-time verify token.
- Host/Name field semantics are the #1 copy-paste failure across Cloudflare (Name), Namecheap (Host), and GoDaddy (Name): panels expect the relative label `_dnstall` (or `@` for apex), not the FQDN; pasting `_dnstall.example.com` or a trailing dot commonly double-appends the zone and yields NXDOMAIN while the publisher believes they “followed instructions.”
- Registrar ≠ authoritative DNS is the silent abandon path: GoDaddy docs state TXT must be created at the company whose nameservers the domain uses; Namecheap+Cloudflare NS (very common) makes registrar-panel edits inert—publishers edit the wrong control plane until they notice Custom NS / Advanced DNS locked.
- Route53 has sharp edges other UIs hide: TXT values often must be double-quoted; strings >255 chars need multi-string concatenation; multiple TXT RRset values are “one record set, one value per row,” and the console’s “record already exists” error looks like a hard conflict even though multi-TXT is legal DNS.
- GoDaddy adds process friction on top of DNS: Domain Protection can force extra identity/2SV before save; official copy still markets “most changes ~1 hour, up to 48 hours,” which inflates abandonment during `di verify` retries even when authoritative answers updated in minutes.
- Namecheap Advanced DNS has documented panel brittleness (support-ticket-only TXT fixes that later UI edits clobber; UI crashes on trailing `.`; multi-hour effective lag vs Cloudflare-fast zones)—median “≤10 minutes unassisted” is registrar-dependent, not universal.
- Underscore labels are intentional for service records (`_dmarc`, `_domainkey`, `_dnslink`) and are generally accepted for TXT today, but historical GoDaddy/SES underscore CNAME UI bugs and non-tech fear of “invalid hostname” still cause support load—publishers need explicit reassurance that `_dnstall` is correct and must not be proxied (Cloudflare orange-cloud only applies to address records anyway).
- Org/npm-publisher reality often breaks DIY setup: domain DNS lives in Terraform/Route53 or an IT ticket queue; Gate 2’s “publisher completes setup without maintainer editing DNS” fails when the package author is not the DNS operator—IaC snippets and ticket-ready change text matter more than prettier registrar screenshots.

### slopsquatting-agent-mitigations-adoption-2026

- What shipped and is actually recommended is package-manager cool-downs (pnpm minimumReleaseAge ~2025-09, Yarn npmMinimalAgeGate, Bun minimumReleaseAge, npm min-release-age ~2026-02), plus Dependabot cooldown / Renovate minimumReleaseAge defaults—not domain continuity. Industry writeups treat age gates as the high-leverage, low-friction control for fresh malicious publishes, including short-lived slopsquat payloads.
- Authoritative guidance (CSA Apr 2026 research note; practitioner CI guides) ranks agent allowlist + human review for any new package install as the top control for agentic workflows; without an allowlist, disable automated package install. That is policy tooling, not a new install UX.
- Hallucination is measurable and predictable: USENIX Security 2025 (~2.23M samples, 16 models) reported ~19.7% samples with ≥1 fabricated package name and high name recurrence across re-prompts (~43% every run / ~58% more than once), so attackers can pre-register model-stable names. 2026 frontier replications still show non-zero rates (~4.6–6.1%).
- Confirmed real-world pressure, not only theory: empty huggingface-cli experiment >30k downloads; unused-imports still drawing weekly downloads after security hold; react-codeshift-style names spreading via AI-generated agent skills / forks (hundreds of repos) with agents executing npx/install. Propagation is documentation and agent skill graphs, not human typos.
- Adopted mitigations cluster around: (1) lockfile pin + hash/install-from-lock only, (2) --ignore-scripts / no lifecycle scripts by default for agents, (3) sandbox install without creds/network post-fetch, (4) registry/scope allowlists, (5) provenance / trusted-publisher + pnpm trustPolicy no-downgrade, (6) install wrappers with malware intel + age block (Aikido Safe Chain ~1.6k GH stars: npm/yarn/pnpm/npx + PyPI, free, blocks very new packages). MCP/live registry validation reduces phantom deps but does not eliminate them (Trend Micro).
- Disconfirming for domaininstall’s core promise on this angle: domain→purl TOFU continuity does not prove a name is what the model meant, and does nothing for first registration of a pure hallucination/conflation (largest classes: fabrications ~51%, conflations ~38%). With zero external publisher _dnstall adoption, a continuity pin cannot gate the names agents invent. DNS/domain mapping also sits against ecosystem moves (Go DNS vanity rejected; Deno walked back freeform URL imports toward JSR).
- Friction evidence on ‘strong trust’ controls: pnpm trustPolicy no-downgrade is opt-in and produces real false positives (cross-major provenance date comparisons; ERR_PNPM_TRUST_DOWNGRADE), driving exclude lists—developers adopt blunt cool-downs more willingly than nuanced identity/provenance continuity. Domaininstall’s comprehension/publisher gates face the same friction profile.
- Install-time script execution remains the primary payload path for agent installs; platform advice converges on ignore-scripts + sandboxed install + no ambient credentials. domaininstall’s existing --ignore-scripts + show exact resolve/npm command aligns with practiced advice more than TOFU continuity does for slopsquatting.

### npm provenance/trusted publishers vs domain continuity

- Orthogonal claims: npm provenance (Sigstore/SLSA) attests build origin (repo + commit + CI workflow); trusted publishers attest publish auth via OIDC-bound workflows (no long-lived tokens); domaininstall attests domain→purl declaration continuity (TOFU). None of these prove package safety or code honesty—npm docs state provenance does not guarantee absence of malware, matching domaininstall's non-goals.
- Consumer enforcement gap favors policy tools: provenance is optional at publish; consumer check is post-install `npm audit signatures` (counts verified attestations). There is no native install-time 'require provenance for package X'—commentators note uptake is low enough that policy must target package lists. This is closer to domaininstall's agent/CI allowlist bet than to expanding install UX.
- Adoption still sparse vs platform marketing: Exaforce/NHIMG (2026) reported only 26/205 (~12.6%) of highly downloaded jsDelivr packages that publish from GitHub Workflows had provenance enabled—so 'green badge ecosystem' is not a saturated substitute for an alternate identity signal.
- Disconfirming (continuity of build identity can catch attacks): axios 1.14.1 (Mar 2026) was published with a stolen long-lived npm token and lacked OIDC/provenance, while legitimate 1.x releases used trusted publishing—forensic mismatch was 'dropped provenance / non-CI publisher,' not a domain map. Trusted publishing only closes this if legacy tokens are disallowed (npm recommends 'disallow tokens' after OIDC setup).
- Disconfirming (provenance can notarize malware): TanStack / Mini Shai-Hulud (May 2026) published ~84 malicious versions with valid trusted-publisher provenance after CI compromise (Pwn Request → cache poison → OIDC token from runner memory). Provenance answered 'right pipeline,' not 'honest pipeline'—first widely cited worm with validly attested malicious npm packages.
- Identity binding gap remains: trusted publisher binds package→specific CI workflow (repo/workflow file); provenance binds tarball→that build. Neither binds a human-memorable domain (or 'official website') to the purl. Thought experiments (e.g. domain-verified handles / DID scopes) argue Sigstore alone lacks strong identity-to-source declaration; domain TXT maps target that different edge.
- Trusted publishers are industry-standard publish hygiene (OpenSSF; GA on npm ~Jul 2025; also PyPI/RubyGems/crates/NuGet), auto-emitting provenance on GH/GitLab OIDC—not a consumer install product. Competing for publisher attention on 'one more security setup' is the real rivalry with `di setup`, not cryptographic overlap.
- Comprehension risk: market language collapses 'supply-chain trust' into provenance badges + OIDC + release cool-downs. Domaininstall can be misread as a weaker provenance clone unless claims are explicit (continuity of declaration ≠ publisher account control ≠ SLSA build integrity).

### PM cool-downs & trustPolicy vs di

- Sep 2025–Feb 2026: pnpm/Yarn/Bun/npm all shipped min-release-age cool-downs (minutes/days/seconds differ); pnpm 11 defaults minimumReleaseAge=1440 with exclude/strict knobs—consumer time-quarantine is now baseline, not niche.
- Cool-downs only shrink the detection window after a bad publish (often hours); they do not fix wrong-package selection, long-lived malware, domain hijack, or publisher intent—so they are orthogonal to domaininstall’s domain→purl continuity claim.
- pnpm trustPolicy no-downgrade (default off) is registry-side TOFU on provenance strength (trusted publisher > provenance > none) to catch stolen-token laptop publishes; it still does not bind domain identity to package name.
- Script-blocking defaults (pnpm allowBuilds, Yarn/Bun scripts off, npm moving toward strict allowlists) commoditize domaininstall’s --ignore-scripts hygiene; selling di as safer npm install is increasingly false differentiation.
- Disconfirming: cool-downs need zero publisher buy-in while di requires live _dnstall TXT—native PM gates dominate the ‘easy supply-chain win’ narrative and make external publisher adoption harder, not easier.
- Cool-downs are bypassed if Renovate/Dependabot/PRs ignore PM age gates or pinned packageManager predates support; real policy enforcement is migrating to agent/CI config layers above any single CLI.
- Unit/name fragmentation (npm days, pnpm minutes, Bun seconds, Yarn npmMinimalAgeGate) creates demand for meta-policy tools—not another install CLI that reimplements age gates.
- Together, age gate + trustPolicy + script allowlist still leave name/namespace confusion (slopsquatting, unofficial packages) unsolved—the residual niche for domain continuity if messaging stays strictly non-malware.

### Go vanity HTTPS success vs rejected DNS TXT #26160

- Proposal 26160 (Sam Whited, 2018) would map go-import content into DNS TXT (e.g. go-import.example.net) with DNSSEC required unless -insecure, falling back to HTTPS; it was closed by rsc as not planned.
- rsc’s rejection was problem/solution mismatch: DNSSEC does not clearly reduce expired certs, bespoke-server bugs, timeouts, cost, or debug pain vs HTTPS; many operators find DNS/DNSSEC harder than a static HTTPS page; dual DNS+HTTPS risks nondeterministic divergence.
- Vanity imports succeeded as language-native package identity and host-portability (domain brand in the import path), reinforced by status signaling—not as a malware or publisher-account security product.
- Load and reliability for popular vanity hosts were addressed by proxy.golang.org and zero-config HTTPS hosts (GH Pages, App Engine, Netlify, etc.), not by adding a second discovery plane—ecosystem invested in making the existing mechanism trivial.
- Disconfirming for domaininstall: Go still uses HTTPS go-import for custom domains even after modules; the DNS path was rejected despite similar ‘everyone already has DNS’ arguments domaininstall relies on for publisher ease.
- Domain control is a brittle trust root: community research has found expired/registrable vanity domains that could hijack module identity; TOFU/sumdb-style continuity is required because DNS/domain ownership alone is not ongoing safety.
- Publisher incentive differed: Go authors gain a permanent, nicer import path under their brand; npm already has registry names, so _dnstall is optional continuity/branding on top—weaker organic adoption force unless setup is near-zero and the continuity story is clear.
- Corporate environments that intercept or restrict DNS have already broken some vanity setups; pure TXT discovery can be worse than HTTPS-to-registry in locked-down CI—favor policy/allowlist consumers over assuming universal DNS-based install.

### Deno HTTP→JSR: domain identity vs install path

- Deno’s official post lists four HTTP-import failures at scale: long/unmemorable URLs, painful multi-file version management (deps.ts), no real semver so duplicate copies of the same library, and reliability/brand damage when any third-party host in the graph is down (CI/new deploys brick despite local cache).
- The strategic pivot is re-centralization of sharing: JSR for published modules, import maps for short names, semver for dedupe; HTTP imports remain for small scripts and niche embeds, but are not the recommended package-sharing path. JSR packages are forbidden from HTTPS imports specifically because semver-based dependency deduplication is impossible with pure URL identity.
- JSR still fetches over HTTP under the hood (jsr:@scope/name → https://jsr.io/...), so the lesson is not ‘URLs are bad’ but ‘users must not manage URL identity as the primary specifier’—registry/name + version, with URL as transport.
- Disconfirming for pure domain-as-install-identity: community writeups (e.g. Jim Nielsen, David Bushell) and HN read the move as abandoning web-decentralized module identity toward npm-like ergonomics; short bare names and package.json-like maps won over domain/URL-native identity for mainstream DX.
- Disconfirming for ‘central registry always wins cleanly’: Bushell documents ecosystem fragmentation—pre-JSR Deno libraries with HTTP deps cannot publish to JSR until the whole chain migrates; deno.land/x packages and dual registries create chicken-egg cost. Domaininstall’s zero publisher adoption faces the same supply-side gate Deno hit when changing the publish/consume contract.
- Security/continuity nuance from discussion: decentralized hosts can mutate content or vanish; Go’s response was a default module proxy with optional direct fetch, not abandoning path-based identity. Deno chose a first-party registry with immutability guarantees instead of TOFU-over-DNS. Domaininstall’s TOFU pin of domain→purl continuity is closer to Go’s ‘identity + pin/proxy’ family than to Deno’s original ‘fetch whatever the URL returns today’ model.
- Where domain/URL identity still works: customer sandboxes and single-file scripts that intentionally import remote code; browser-parity ESM. Those are policy/allowlist and small-scale use cases—not ‘replace npm for every transitive dep.’
- Market narrative alignment: ecosystem direction (npm provenance/Sigstore, min-release-age cool-downs, trustPolicy) is about registry-time trust and version gates, not about making the domain the package graph. Domaininstall’s non-goals (not malware scanner, not attestations system, not registry replacement) match what Deno effectively re-learned: identity ≠ safety and decentralization ≠ operable dependency management.

### CI/agent install allowlist policy

- Security guidance (CSA 2026, agent threat writeups) treats explicit package allowlists + human review for non-listed installs as the primary control for AI agents with package-manager tools—not domain continuity, provenance, or malware scores alone.
- Package managers themselves shipped free, zero-publisher install gates (pnpm/yarn/bun/npm/Deno min-release-age cool-downs; pnpm trustPolicy no-downgrade; npm moving toward default script allowlists). These satisfy much of the 'don't pull brand-new compromised releases' demand without any third-party CLI or _dnstall adoption.
- Socket Firewall Free / safe-npm wrap package managers and block on malware/risk signals before write-to-disk; Free has no package allowlist (Enterprise does). They compete on install-time interception and work with zero publisher cooperation—domaininstall's opposite supply constraint.
- npq remains a lightweight open pre-install heuristic gate (lifecycle scripts, age, repo, typos, etc.) with auto-continue defaults; it is an audit prompt, not a deny-by-default org policy engine, and still needs no publisher setup.
- Install-script allowlists (LavaMoat allow-scripts; npm allow-scripts / npm 12 direction) only control who may run lifecycle hooks after install—not which names/versions may enter the tree. domaininstall's --ignore-scripts already overlaps this layer; name/version allowlisting is the underserved agent gap.
- Enterprise org allowlists are largely owned by private registry / proxy products (Cloudsmith, Nexus, Artifactory) with policy engines and quarantine—not by domain-to-purl binding. Lightweight open agent/CI policy is less saturated than 'replace the enterprise proxy'.
- Disconfirming for domaininstall-as-allowlist: zero _dnstall publisher adoption means a continuity-gated allowlist is empty; domain→purl TOFU does not stop same-package malicious versions (e.g. compromised maintainer) or slopsquatting names that never had a domain mapping; agents need name/purl gates that work from lockfiles today.
- Agents amplify classic vectors (lockfile regen, unattended npm install, broad secrets on runners, skill/plugin install surfaces). Demand is for fail-closed, non-interactive, machine-readable policy (exit codes, JSON), not interactive install UX or malware scanning claims.

### MCP/agent package install: resolve-by-domain demand

- No public evidence that coding agents or MCP workflows request domain→npm resolution; agent tooling demand is pre-install package validation (exists?, malware?, CVE?) on registry names/versions (Endor Labs MCP tools; Augment reports validation MCP improved safety ~3×).
- Primary agent install failure mode is slopsquatting/hallucinated registry names (Endor: high hallucination rates among agent-chosen deps; Aikido: react-codeshift referenced in 237+ skill repos with live agent download trickle)—domain→purl continuity does not address invented package names.
- Skills/MCP markdown instructions act as executable install playbooks (npx/bunx/pnpm dlx) that agents follow without existence checks; market asks for verify-before-run, not human-friendly domain install UX.
- DNS-for-agents momentum is discovery of agents/MCP servers (Linux Foundation DNS-AID, IETF DAN drafts), not software package mapping; separate research shows DNS TXT as an agent instruction-injection surface—weak optics for install-trust via TXT.
- Enforcement patterns agents actually meet are allowlists and install interceptors: Claude Code network domain allowlists, Socket Firewall wrappers/proxies, private registry allowlists, npm v12 allowScripts/git/remote defaults off, pnpm onlyBuiltDependencies—policy gates, not domain install CLIs.
- domaininstall’s publisher-supply constraint is fatal for agent productization of domain resolve: agents emit package names from training/skills; without widespread _dnstall records, resolve-by-domain is empty while SCA MCP tools work on day one against npm.
- Install-with--ignore-scripts is less differentiating in 2026 as package managers default scripts off or allowlist builds; agents still need identity/allowlist decisions after scripts are disabled.
- Disconfirming product implication: expanding the human CLI around domain install does not match agent workflows; the nearer wedge is machine-readable resolve/policy (JSON/MCP) used as an optional org pin, not the primary package selector.

### DNSLink & domain-linked resources

- DNSLink’s hard-won underscore convention (_dnslink.) exists because apex/root TXT collides with CNAME/ALIAS and blocks secure delegation; domaininstall’s _dnstall. is the right shape, and legacy root-TXT support becomes a long-lived bug surface (DNSLink still resolves deprecated apex TXT “for legacy”).
- DNSLink adoption is real but ecosystem-captive: live usage clusters around IPFS-native sites (ipfs.tech, libp2p, wikipedia-on-ipfs) where gateways/Companion already resolve it—publishers outside that client loop have near-zero reason to maintain records. That mirrors domaininstall’s publisher-supply bind at 0.0.3 with zero external adoption.
- Go’s DNS-TXT vanity-import proposal never became the toolchain path: it demanded DNSSEC for parity with HTTPS vanity, which is non-ubiquitous, while HTTP+TLS vanity already worked and the ecosystem later re-centered on modules/proxy.golang.org. Pure DNS mapping without security that actually ships + without client monopoly loses to “good enough HTTPS.”
- Deno’s URL/domain-linked import dream scaled poorly: long unstable identifiers, no semver dedup, and least-reliable-host failure modes; they kept the mechanism but redirected product gravity to JSR + import maps. Domain→purl is more stable than raw URLs, but “point at a mutable host/name” still fails as the primary trust or version story.
- Operational friction is structural, not fixable by CLI polish alone: every registrar has different APIs (DNSLink docs admit no standard write path), TTLs are ignored by many resolvers so both “low TTL for quick revokes” and “high TTL for stability” are unreliable for security decisions, and multi-TXT order is nondeterministic without client-side sort rules.
- DNS control is not package safety: DNS names are rented, seizable, and censorable; TXT is a known C2/exfil and governance blind spot. A _dnstall record proves domain-zone write access at query time, not continuous npm account control, malware absence, or non-transfer of the domain—exactly domaininstall’s stated non-promise, which markets will still misread without aggressive disclaimers.
- The production pattern that actually works for domain-linked pointers is delegated sandbox zones: CNAME _dnslink.example.com → a restricted zone with CI tokens that cannot touch A/MX/NS. Without that, automated di setup either requires scary full-zone credentials or stays a manual dig/UI chore publishers skip.
- Disconfirming for CLI expansion: DNSLink never needed to replace npm/HTTP for mainstream install; it survived as an optional resilience layer for a niche stack. If continuity verification has no buyer (publishers + policy engines), growing di subcommands repeats a pattern of rich resolvers with empty zones.

### multi-PM support complexity (pnpm/Yarn/Bun)

- Safe install is not portable: npm --ignore-scripts, pnpm allowBuilds/onlyBuiltDependencies (scripts off by default since v10), Yarn Berry enableScripts:false + dependenciesMeta.built, and Bun trustedDependencies are four different contracts; a shared --ignore-scripts mapping would misstate guarantees.
- Bun docs treat --ignore-scripts as primarily skipping project package.json lifecycle scripts while dependency scripts are already restricted (and allowlisted via trustedDependencies)—flag-name reuse is a security footgun for di’s ‘always ignore-scripts’ promise.
- Yarn Classic vs Berry share yarn.lock naming but differ in binary resolution (Corepack/yarnPath), config surface, and script controls; ‘support Yarn’ is at least two backends, not one.
- By mid-2026, default-deny or allowlisted lifecycle scripts are table stakes across major JS PMs (pnpm 10+, Yarn Berry, Bun, npm 12)—multi-PM install does not differentiate domaininstall’s unique DNS continuity/TOFU value.
- Packagegate-class research showed manager-specific ignore-scripts/git-prepare gaps; each extra PM multiplies the adversarial test matrix already tracked as ROADMAP G5 rather than a thin adapter layer.
- domaininstall already invests heavily in npm-only Windows no-shell spawning (npm.cmd → npm-cli.js); pnpm.cmd/yarn.cmd/bun.exe reintroduce launcher/shell injection complexity without advancing publisher supply, the stated binding constraint.
- Command shape and resolution flags diverge (npm install vs pnpm/yarn/bun add; registry and exact-version options), so the product promise to show the exact resolve+install command requires per-PM plan builders, not a single argv template.
- Disconfirming user pain is real (non-npm projects are refused today), but wrong-PM install is worse than refuse: detection ambiguity (packageManager field, multiple lockfiles, monorepos) can silently run the insecure path if multi-PM is half-implemented.

### RDAP domain registration monitoring & hijack defenses

- Security products (Oh Dear, Hardenize, Uptime.com, WhoisFreaks, DomainTools) treat RDAP as a structured JSON baseline: poll for expiry, EPP statuses, registrar/NS drift, and domain disappearance—not as package or code trust.
- The high-signal hijack-adjacent field is EPP transfer/update locks (e.g. clientTransferProhibited); tools alert when locks vanish or unauthorized registrar/nameserver changes appear—detection after or during compromise, not cryptographic prevention.
- Disconfirming: public RDAP is heavily privacy-redacted post-GDPR, so tools generally cannot bind domain control to a stable registrant identity; RDAP does not prove continuous legal ownership of the domain behind _dnstall.
- Disconfirming: coverage and reliability remain incomplete—ccTLD RDAP adoption lags gTLDs, endpoints rate-limit, and mature monitors still keep WHOIS/web fallbacks; domaininstall cannot assume universal RDAP for all publisher domains.
- Successful domain hijack or post-expiry re-registration typically grants DNS authority, so an attacker can rewrite _dnstall TXT; consumer TOFU pins and RDAP monitoring sit on different layers and do not automatically compose into proof of package safety.
- Market context: continuous RDAP drift/expiry monitoring is a crowded uptime/brand-protection category (often daily to ~10-minute polls); building a full monitor inside CLI di would compete with Oh Dear-class products and not solve publisher onboarding.
- Operational defense hierarchy used in practice is registrar-side prevention first (transfer lock, registry lock, 2FA, auth-code hygiene), independent RDAP/WHOIS monitoring second, DNSSEC/NS integrity third—none of which replace npm provenance, lockfiles, or ignore-scripts install policy.

### Transparency logs vs first-use TOFU

- Local TOFU only protects returning clients with durable state; in package installs and ephemeral CI it becomes trust-on-every-use (Lorenc), which matches domaininstall’s pin store and ROADMAP G10 first-user gap.
- Go sumdb-style transparency turns TOFU global: the first ecosystem observation of a version is append-only and shared, so targeted MITM of one client is harder—but the first global observation can still be malicious and is then sticky forever.
- OpenSSF/Rekor guidance is disconfirming for ‘log entry = safe’: transparency does not make packages or mappings trustworthy; it enables monitoring for unexpected signing or checksum events after the fact.
- Security value of CT/Rekor depends on active monitors; CT research shows domain owners cannot reliably self-monitor, third-party monitors miss certs, and monitoring is under-adopted—so an unmonitored domaininstall log would be forensics theater, not prevention.
- Append-only permanence is a product liability: mistaken or hostile first sumdb entries cannot be quietly removed; a global first-seen _dnstall map needs explicit rekey/revocation UX, not silent pin overwrite.
- npm provenance + Sigstore Rekor attest build identity, not domain→purl continuity; domaininstall’s narrow continuity claim is orthogonal and must not be marketed as log-backed without log+gossip infrastructure.
- Local pin expansion alone does not close domain expiry/hijack first-install (ROADMAP R5) or CI bootstrap; that disconfirms expanding the install CLI for ‘more TOFU fields’ and supports agent/CI pre-seeded allowlists as the higher-leverage control.

### publisher-supply-before-demand (devtool marketplace)

- Standard two-sided strategy seeds the harder side first: domaininstall’s zero external _dnstall publishers means consumer install UX cannot produce network effects until records exist; concentrate on curated density, not global CLI reach.
- DISCONFIRMING—Reforge supply-feature trap: suppliers value incremental demand over SaaS-like setup polish; over-investing in di setup satisfaction metrics without resolve/install liquidity or solo-side ROI recreates dead marketplace tooling.
- Bridge pattern (OpenTable): when marketplace demand is empty, supply needs standalone value—brand claim, anti-slopsquatting domain→pkg continuity, badge/README signal—not ‘join an empty di installer network.’
- Demand→supply loops (Eventbrite/Square ~0.5–5% conversion) only amplify after demand-side usage exists; Rothenberg: do not force this from cold start—domaininstall has neither side at meaningful scale yet.
- npm maintainer survey (n=75, 2026): time is #1 security barrier; only ~40% satisfied with security tools (noise/FPs); automated low-friction practices win—DNS TXT + TOFU is another chore unless one-command and payoff is immediate.
- Even first-party npm provenance/Sigstore (~3.8k beta projects) and trusted publishing remain opt-in, non-enforced at install, with onboarding friction—third-party DNS TOFU with weaker guarantees faces a steeper voluntary publisher hill.
- 2026 demand substitutes undercut pull: min-release-age, pnpm trustPolicy, provenance/audit signatures, CI allowlists address supply-chain fear without any _dnstall map; domaininstall explicitly does not prove malware-free or account control.
- Go DNS vanity-import proposal shows DNS package metadata is contested (ops/DNSSEC/corporate DNS); treat DNS as publisher cost, measure success as live records + resolve hits, not CLI downloads.

### Enterprise/offline DNS resolution constraints

- True air-gapped/defense installs cannot perform live public DNS at install time: standard patterns are pre-approved internal mirrors (Nexus/Artifactory/Verdaccio for npm), Harbor/media transfer, and fully self-contained artifacts—so _dnstall TXT dig is architecturally unavailable on the path domaininstall would need.
- Enterprise dependency admission is allowlist/mirror-first with security review of new packages before they enter the enclave; dynamic public domain→purl discovery is the opposite control model (discovery vs. fixed admission).
- Security programs treat unusual DNS TXT traffic as high-risk (tunneling/C2/exfil; SUNBURST-class DNS abuse). Guidance includes restricting TXT lookups on user networks and proxying only known domains—novel client queries to _dnstall.<arbitrary-publisher> can break or alert under protective DNS.
- 2026 TXT-governance push (inventory, classification, lifecycle, change monitoring) means publisher _dnstall records face DNS change-control and “unknown record” scrutiny—another brake on publisher supply, not just end-user CLI friction.
- DNSSEC cannot underwrite domaininstall integrity for most clients: validation/signing remain partial (APNIC-class figures still well below universal; resolver awareness often ~low teens %), so unauthenticated recursive DNS remains spoofable—weaker than HTTPS vanity or registry/provenance controls.
- Go’s DNS-TXT vanity-import proposal never became standard; the winning enterprise pattern for offline/reliability was module proxies and caches (GOPROXY-style), not live DNS control-plane lookups—cautionary precedent for DNS-as-package-metadata.
- Disconfirming nuance: semi-connected corporate laptops often still allow outbound DNS when HTTP egress is locked, so dig may “work” offline-of-npm; that is still the wrong product bet because security ops prefer fixed policy artifacts over new DNS semantics, and high-entropy purl TXT payloads can look like tunnel traffic.
- OpenSSF/Zarf-style air-gap DevSecOps verifies SBOM/signatures on the connected side then deploys offline bundles—continuity must travel as a portable pin/allowlist artifact, not as a runtime dig of public DNS.

### README install-by-domain vs npm i

- Disconfirming: consumer security wrappers (Socket safe-npm, npq) almost never become the primary README install line; authors still ship `npm i <pkg>`. domaininstall faces the same placement gravity unless it is optional, one-shot, and non-security-framed.
- Disconfirming: Deno publicly walked back URL/host-centric module identity toward JSR short names (URL length, host reliability, missing semver). Maintainers who lived that arc will treat domain-as-install-identity as a known dead end for day-to-day JS DX.
- Disconfirming: 2026 README/security attention goes to registry-native controls (min-release-age across npm/pnpm/yarn/bun, pnpm trustPolicy, trusted publishing/provenance badges)—not third-party install CLIs. Competing for install-doc space against those is a loser's game.
- Disconfirming: honest product scope (domain→purl continuity/TOFU only; no malware or publisher-account proof) undermines a security-flavored README CTA after account-takeover incidents; sophisticated maintainers will refuse a second install path that doesn't reduce the attack they fear.
- Confirming pattern from Go vanity: custom-domain package identity sells as brand seriousness and forge/portability, not as a scanner. domaininstall is more README-plausible as 'official package for this domain' than as 'safer install'.
- Users copy-paste README install lines blindly—but only if the line is short and tools are already present. Requiring global `domaininstall` + verify + install is multi-step vs one-liner `npm i`; placement fails without zero-install invocation (e.g. `npx`/`npm exec`).
- Slopsquatting pressure is real but agent/CI-shaped: hallucinated package names are not fixed by a human README `di domain` note. Publisher DNS helps brand owners; policy/allowlist consumers are the clearer demand side if publisher README gates fail.
- Only a thin publisher segment has incentive: domain owners where brand domain ≠ npm name, name-confusion risk, or existing DNS ops maturity. Zero external mappings today is consistent with weak README ROI for everyone else.
